## 输出要求

请以Markdown格式输出系统设计方案。不要用JSON包裹，直接输出Markdown文本。包含以下章节：

### 1. 系统概述

### 2. 系统分层架构

### 3. 模块划分
列出系统的功能模块，每个模块包含：
- 模块名称
- 模块职责
- 对应的功能需求ID

硬性约束：
- 每个功能 ID 只能映射到语义匹配的模块，不能为了覆盖率把不相关 ID 塞进模块。例如日志审计类功能必须进入日志/审计/运维类模块，不能放进用户认证模块。
- 模块表必须覆盖 `requirement_json.functions[].id` 的全部 ID，且不要新增不存在的功能 ID。

格式示例：
| 模块名称 | 职责描述 | 对应功能 |
|----------|----------|----------|
| 用户管理模块 | 处理用户注册、登录、权限管理 | F001, F002 |

### 4. 核心类/接口设计
列出系统中的核心类或接口，每个包含：
- 类名
- 职责描述
- 主要属性（3-5个关键属性）
- 主要方法（3-5个关键方法）
- 关联的实体

格式示例：
| 类名 | 职责 | 关键属性 | 关键方法 |
|------|------|----------|----------|
| 用户 | 用户实体 | 用户ID, 用户名, 邮箱, 角色 | 注册(), 登录(), 更新资料() |

硬性约束：
- 核心领域类必须严格来自 `requirement_json.entities[].name`，大小写必须完全一致。
- **禁止改名**：如果需求分析中有一个实体叫 `Review`，你不能在设计里把它改成 `Evaluation` 或 `Comment`。必须使用完全相同的英文名。
- 不要把 `OrderItem`、`Payment`、`SKU/Sku` 等未出现在 `entities` 中的概念提升为核心领域类；如确实需要，只能作为某个实体的属性或实现细节说明。
- 如果实体属性里包含列表或嵌套对象，优先作为属性描述，不要自动拆成新核心实体。
- **角色实体合并**：如果角色（如 Customer、Merchant、Admin、WarehouseManager）仅仅是 User 的身份标签，只有 id 和 status 属性而没有独立的业务属性和行为，不要将它们列为独立的核心类。应该在 User 类中用 role 字段（如 roles: String[] 或 role: String）来表示。只有当角色有独立于 User 的专属属性（如商家有店铺、仓库管理员有所属仓库）时，才单独建类。
- 输出前做一次实体名自检：逐一核对 `requirement_json.entities[].name` 列表，确认每个实体都在核心类表中有对应条目，且类名完全一致。如果发现遗漏或改名，立即修正。
