## 输出要求

请只输出合法 JSON，不要输出 Markdown、代码围栏或解释文本。根对象必须包含 `test_cases` 数组。

### 测试用例类型要求：

1. **正常场景**（至少3个）：覆盖主要功能的正常使用流程
2. **异常场景**（至少2个）：覆盖错误输入、权限不足、状态异常等情况
3. **边界场景**（至少2个）：覆盖空值、极值、特殊字符等边界条件

### 风险覆盖要求：

生成测试前先从需求中构造覆盖矩阵，并把矩阵落实为用例：
- 每个功能 ID 至少一个正常用例；每个 `sub_capabilities` 至少被一个步骤或预期结果覆盖
- 每条数值/金额/数量约束必须覆盖：边界内、等于边界、超出边界；若输入范围和结果范围存在歧义，必须增加“结果超出范围”的澄清型边界测试
- 每条时间约束必须说明如何模拟时间（如冻结时钟、设置订单创建时间、触发定时任务），不能只写“等待 72 小时”
- 涉及锁定/库存/支付/退款/优惠券/物流/状态机的系统，必须覆盖状态竞态和补偿：锁定后支付超时释放、优惠券在下单和支付之间过期、部分退款、重复支付回调、并发扣减或回滚
- 测试步骤必须可执行、可验证，不能用“系统扫描一下”“检查是否正常”等笼统表述

### 优先级定义：
- P0：核心功能，必须通过
- P1：重要功能，应该通过
- P2：辅助功能，可以后续补充

### 编号规则：
- 正常场景：TC-N-001, TC-N-002, ...
- 异常场景：TC-E-001, TC-E-002, ...
- 边界场景：TC-B-001, TC-B-002, ...

JSON Schema：
{
  "test_cases": [
    {
      "id": "TC-N-001",
      "title": "用户登录成功",
      "type": "正常",
      "target": "F001 用户登录",
      "preconditions": "用户已注册",
      "steps": ["输入正确用户名", "输入正确密码", "点击登录"],
      "expected_result": "登录成功，跳转首页",
      "priority": "P0"
    }
  ]
}

字段要求：
- `id`: 必须使用 TC-N/TC-E/TC-B 前缀
- `title`: 简短说明测试目的
- `type`: 只能是 正常、异常、边界
- `target`: 必须包含真实的功能 ID；异常用例还应包含真实异常 ID
- `steps`: 字符串数组，每一步可执行
- `expected_result`: 明确可验证
- `priority`: 只能是 P0/P1/P2

注意：
1. 测试用例必须与需求分析中的功能点一一对应
2. 每个 `functions[].id`（如 F001、F002）必须至少出现在一个测试用例的 `target` 字段中
3. 每个功能需求至少有一个正常场景测试用例
4. 核心链路功能还应至少补充一个异常或边界场景
5. 总测试用例数应不少于功能需求总数的1.5倍
6. 测试步骤要具体可执行
7. 预期结果要明确可验证
8. 每个 `exceptions[].id` 必须至少在一个测试用例的 `target` 或 `steps` 字段中被引用
9. 不要发明新的功能 ID 或异常 ID；只能使用 requirement_json 中真实存在的编号
10. 优先级只能使用 P0/P1/P2，禁止使用 高/中/低
11. **每个 `constraints[].id` 必须至少出现在一个测试用例的 `target` 字段中**，且该测试用例必须是边界场景或异常场景。例如 C003（库存约束）应有独立的边界测试：库存预警阈值、超卖比例等
12. 如果需求中包含 `sub_capabilities` 或 `acceptance_criteria` 字段，必须逐项覆盖；不要只覆盖顶层功能 ID
